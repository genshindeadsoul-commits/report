# Student Performance Report Generator

Generate professional, personalized student performance reports (PDF & Word)
from a simple form or a bulk Excel upload — no manual calculation, no
repetitive report-writing.

```
student-report-generator/
├── frontend/            Next.js + TypeScript + Tailwind UI
├── backend/              FastAPI app + the report engine
│   └── app/
│       ├── main.py               FastAPI entrypoint
│       ├── routes/reports.py     API routes
│       ├── services/             Excel processing + report assembly
│       ├── models/schemas.py     Pydantic request/response models
│       └── report_engine/        Pure calculation & generation logic
├── sample_data/          10-student sample Excel file + generator script
└── README.md
```

## 1. Quick start

### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

The API is now live at `http://localhost:8000`. Interactive docs (Swagger UI)
are auto-generated by FastAPI at `http://localhost:8000/docs` — a fast way to
try every endpoint (preview, generate PDF/DOCX, upload Excel, bulk ZIP,
combined PDF) without the frontend.

### Frontend

```bash
cd frontend
cp .env.local.example .env.local     # points the UI at http://localhost:8000/api
npm install
npm run dev
```

Open `http://localhost:3000`.

### Try it immediately with the sample data

```bash
cd sample_data
python3 generate_sample.py     # regenerates students.xlsx if you want to tweak it
```

Then, with both servers running, go to **Upload Excel** in the UI and upload
`sample_data/students.xlsx` — you'll get 10 visibly different reports
(an outstanding student, a poor-attendance student, one requiring
significant improvement, and so on).

## 2. How a report is built (report engine)

Everything under `backend/app/report_engine/` is pure, testable Python with
no I/O — you can run it without a server:

```python
from app.report_engine import calculate_subject_grades, build_insights, generate_remark, DEFAULT_CONFIG

subject_rows = calculate_subject_grades(
    {"Mathematics": 91, "English": 78}, {"Mathematics": 100, "English": 100}, DEFAULT_CONFIG
)
```

- `calculations.py` — total marks, percentage, attendance %, grade lookup
- `analysis.py` — strongest/weakest subject, performance band, attendance
  band, term-over-term improvement
- `remark.py` — builds a personalized paragraph from the student's actual
  numbers (no AI needed). Different students reliably get different
  phrasing because sentence variants are chosen deterministically from a
  hash of the student's own data.
- `docx_generator.py` / `pdf_generator.py` — turn the assembled report data
  into a polished `.docx` (python-docx) or `.pdf` (ReportLab)
- `ai_enhancer.py` — **optional**. Only runs if `ANTHROPIC_API_KEY` or
  `OPENAI_API_KEY` is set in the environment, and only ever rewrites the
  *tone* of the already-generated paragraph — it is never given raw marks
  and can't affect any calculation.

Grading bands, performance bands, attendance bands, the school name, and
academic year are all in one place: `report_engine/config.py`. Change the
`GradingConfig` there (or pass a different one into the service layer) to
retune grading without touching any calculation code.

## 3. API reference (key endpoints)

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/reports/preview` | Calculate a report from one student's data (JSON) — for the "review before download" screen |
| POST | `/api/reports/generate/pdf` | Generate one student's PDF |
| POST | `/api/reports/generate/docx` | Generate one student's Word doc |
| POST | `/api/reports/upload` | Upload an Excel file; validates columns + rows, returns parsed students and any flagged issues |
| GET  | `/api/reports/template` | Download the standard Excel template |
| POST | `/api/reports/bulk/zip` | Generate a PDF per student, return as one ZIP |
| POST | `/api/reports/bulk/combined-pdf` | Generate one PDF containing every student's report |

Every route catches internal errors and returns a plain-language message —
teachers never see a Python stack trace.

## 5. Design notes / decisions

- **No database in V1**, per the brief — this is a stateless
  file-in/file-out pipeline. Nothing about a student is stored after the
  request completes.
- **AI is fully optional.** The app calculates and writes remarks entirely
  deterministically; set an API key only if you want the observation
  paragraph rewritten in a slightly different voice.
- **Validation is forgiving but transparent.** Bad rows in an Excel upload
  (missing marks, marks over 100, present days > working days, duplicate
  roll numbers) are auto-corrected to a safe value and flagged in the UI,
  rather than blocking the whole upload — the teacher can still see and fix
  the flagged rows.
- **Report layout** mirrors the brief's V2 design: header with school name,
  student info card, four performance summary cards, subject table,
  automatic insights, attendance block, teacher assessment table,
  highlighted observation box, and a signature line — reproduced
  consistently across both the PDF and Word outputs.

## 6. What's next (deliberately out of scope for V1)

Per the brief, these are intentionally deferred until a school-wide
deployment is needed: teacher/school accounts & auth, a database for
saved students and report history, previous-year comparisons beyond a
single optional `previous_percentage` field, and cloud infrastructure.
The architecture (service layer separated from routes, a config object for
grading, a report_data dict as the single interface into both generators)
is built so those can be layered on without rewriting the report engine.
